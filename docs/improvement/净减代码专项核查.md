## 比减行本身更有价值的无用执行

ProjectService.record_operation 的 payload 参数完全未读取，当前仅发送级别、阶段、状态、消息。前端却有 **8 处**调用仍构造 payload：筛选、RSM、田口、代理模型训练、统计失败、优化统计完成、局部探索完成、手动核验完成。

其中包括 reports.results(project) 全结果序列化、reports.serializable(snapshot) 快照序列化，以及 _analysis_settings 的运行设置收集。它们的返回值被服务直接丢弃。这些构造可删除，同时移除只为该丢弃数据服务的 _analysis_settings；服务仍保留消息通知和正常结果发布。

实施时应把 message 改成明确关键字参数，避免旧的第四位置参数在删除 payload 后错位。正常 publish_results/update_workbench 的序列化仍有消费者，必须保留。此项预计再减约 10–20 行，和前面的 169 行分开核算。

## 第二批：需要改造后才能得出净减量

### 报告直接生成所需内容

实际链路是 build_current_report → build_report → 再删除 history 分节、履历列、人工结论及“未填写”说明，再改标题和状态。build_report 还保留 kind='trial'、record_id、历史版本风险等旧分支，但当前界面只调用单次结果报告，ProjectService 也不再写入 report_history。

应直接构造当前报告所需内容，取消“先构造旧功能再剔除”的两遍处理。预计额外净减约 30–60 行，需保持当前七个分节、公式、图表、空结果、转义与 PDF/HTML 输出；已有直接调用 build_report 的测试要相应改为当前报告接口。这个估算不重复计算前面的档案函数 43 行。

### 同步／异步优化共享准备和结果接收

OptimizationController.run_workbench 和 _execute_workbench 重复做参数读取、上下文准备、优化调用／安排、结果检查、帕累托图、统计更新和完成通知。后者没有界面入口，但 test 中的回归与渲染脚本使用它，不能当作完全无调用代码直接删除。

可以共用准备参数和接收结果，保留线程适配；或把测试改为调用共用计算服务，删除额外同步页面执行路径。预计净减约 15–30 行，必须保留异步进度、界面恢复、输入版本校验和失败处理。不能为省行数取消后台线程。

### 纯转发方法

OptimizationPage 中存在一组调用 controller 或 optimization_panels 后立即 return 的方法，部分产生 Page → Controller → Page → Controller 的回跳。没有行为的构建转发可让构建器直接调用对应实现；控制器内部可直接调用自身方法。

这是取消多余调用层，不是合并业务表达式。它涉及测试的 patch 位置和现有页面接口，不列为第一批；收益应以实际删除的转发方法减去调用改造成本统计，不承诺固定数字。

### 小型界面基础函数

只读表格填充、下拉列表刷新、分节及布局清空仍可复用，但每组一般只有十几／几十行，新增适配也有成本。应排在旧功能删除之后，避免重复上次数值控件“投入明显、净减很小”的情况。
