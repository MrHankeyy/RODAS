核查日期：2026-10-21。目的：在保持界面行为、输入含义和计算结果的前提下，识别值得抽取的重复实现，合理减少维护代码。本轮仅核查并记录，不重构正式代码。

实施进展：用户已确认并完成[数值输入框复用](数值输入框复用实施记录.md)；下方保留实施前核查基线，其余抽取候选尚未实施。

后续重点：[净减代码专项核查](净减代码专项核查.md)，优先检查旧功能、无用执行与重复实现，给出候选体量和不能误删的边界。

## 范围与统计口径

- 静态扫描正式 Python 代码 56 个文件、8,388 物理行：`main.py` 14 行，`frontend/` 26 个文件、4,404 行，`backend/` 29 个文件、3,970 行；包含空行与注释，不计测试、临时脚本、虚拟环境与缓存。
- 使用 Python AST 统计实际构造调用，排除 import、类型判断、样式表中的类名。创建点指源代码中的调用位置，不是运行时控件数量：循环、表格动态增行和参数化面板会生成多个实例。
- AST 清单保存在 `output/reuse-audit/inventory.json`；一次性检查脚本为 `temp/audit_reuse.py`。
- 区分三层：Qt 原生控件复用、项目公共组件／样式复用、业务内容复用。直接构造 Qt 控件不是重新实现该控件；值得抽取的是多次出现的配置和行为，而非单纯替换类名。

### 1. 整数与小数输入

整数创建点分布：`configuration_panels.py` 6 处、`model_configuration.py` 11 处、`optimization_panels.py` 3 处。常见代码重复为“创建控件 → 设置范围 → 设置默认值 → 放入布局”。

代表位置：

- [筛选设计：中心点、重复次数、随机种子](../../frontend/pages/configuration_panels.py:28)。
- [模型设置：样本数、中心点、重复次数、随机种子](../../frontend/pages/model_configuration.py:52)。
- [优化设置：种群数和代数](../../frontend/pages/optimization_panels.py:98)。

小数输入已经有 [局部 `_dspin` 工厂](../../frontend/pages/model_configuration.py:287)，统一范围、精度、默认值和步长，但 [优化面板](../../frontend/pages/optimization_panels.py:109) 5 处及 [设计点核验](../../frontend/pages/workbench_diagnostics.py:90) 1 处没有使用该公共能力。

建议增加两个轻量创建函数，例如 `integer_input(...)` 和 `decimal_input(...)`，明确接受范围、初值、步长、精度等参数。无需创建多层继承体系。业务默认值仍留在调用处，以便审阅。

需要保留的差异：

- 模型超参数使用 3／4 位小数，设计点核验使用 8 位；不能一律设置相同精度或步长。
- `_dspin` 的步长根据范围推导；权重和安全系数有各自步长，不应直接套用同一个默认算法。
- 目前仅样本数输入显式关闭 keyboard tracking。是否统一输入过程中触发信号的行为，需要单独核对，不能把行为变化混入减行数重构。
- 建模页还有 8 个 `QLineEdit` 创建点，其中阈值、P1、P2 共 3 个位置用于数字／数字组合输入，其余包含名称、单位与报告信息。阈值可能是“下限,上限”，并涉及后续正无穷需求，不适合全部换成小数步进框。
- 当前源码未发现 `QIntValidator`、`QDoubleValidator` 等项目级数字校验组件。是否补充属于输入规则改进，不等同于纯代码复用；本次不改变校验语义。

仍有值得抽取的重复：

1. **结果表格的填充实现。** `SummaryTable.__init__`、[DesignResultsPanel.fill](../../frontend/pages/design_results.py:54)、[WorkbenchDiagnostics.fill](../../frontend/pages/workbench_diagnostics.py:55) 都包含设置行列、遍历单元格、格式化数值、数学标记与行高调整。后两者分别接收二维行列表和字典行，显示精度也不同；可以共享填充核心，由小适配层处理列与精度。
2. **结果分节。** `AnalysisResults.section`、`ResultOverview._section`、`RobustResults._section` 分别创建 `QGroupBox + QVBoxLayout`，共 3 处相近结构。可以用一个简短分节函数，避免建立参数众多的通用页面父类。
3. **动态布局清理。** 分析结果、方案汇总、鲁棒结果分别遍历布局并调用 `hide/deleteLater`。可抽取共用清理函数，但净减行收益较小，需要明确是否递归清理嵌套布局。
4. **只读表格初始化。** 筛选／田口表、诊断表、容差表、工具表重复设置只读与表头策略。可共享初始化选项；数据编辑表和因子表不应混入只读结果表。

不建议直接把所有表格替换成 `SummaryTable`：该组件会按行数固定高度，并关闭内外滚动条，适合页面内的短摘要；逐点诊断等长表仍需要自己的滚动和列宽策略。

### 3. 下拉框

已复用：

- [theme.py](../../frontend/theme.py:40) 统一边框、下拉箭头、焦点与选项列表样式。
- [decorate_combo](../../frontend/math_widgets.py:33) 为有公式的选项提供共享数学显示适配；源码有 2 处调用。
- [ConfigurationPage._reset_combo](../../frontend/pages/configuration_page.py:210) 已封装保留当前文本、阻塞信号、重建列表、恢复选择，但目前仅在该页面复用。

明确的重复是 **5 处下拉框列表刷新序列**，分布在 4 个文件：

- `AnalysisResults.set_result`：按 itemData 保留响应选择。
- `ConfigurationPage._reset_combo`：按显示文本保留内／外表选择。
- `DesignResultsPanel.set_result`：刷新响应列表。
- `DesignResultsPanel.render`：刷新绘图因子列表。
- `WorkbenchDiagnostics.set_context`：刷新响应列表。

这 5 处都在做 `blockSignals → clear → addItems/addItem → 恢复或选择 → unblockSignals` 的变体。适合抽取 `replace_combo_items(...)`，明确支持纯文本项、显示值／数据值与选择策略。可使用 `QSignalBlocker` 保留原信号阻塞状态。不能默认所有列表必须保留同一种选择。

单纯把 `QComboBox(); addItems(...)` 改成 `combo(items)` 也可以减行，但部分代码已经放在同一物理行，且业务联动仍须保留，收益不能按“29 处 × 固定行数”计算。

## 其他复用检查

### 已集中实现，应继续保留

- [ModelConfiguration](../../frontend/pages/model_configuration.py:23) 以参数化方式覆盖 RSM、Kriging、SVR、ANN；创建调用位于循环内，不是四份复制页面。
- [ProjectService](../../backend/services/project_service.py:27) 统一输入提交、结果失效与结果发布，不应在各页面另写一套。
- [Workspace / dialog_path](../../frontend/workspace.py:8) 共用本次运行的工作目录；6 个文件对话框调用点复用同一默认位置处理。
- [Notice / MessageBus](../../frontend/notifications.py:5) 统一非模态运行消息。
- [backend/infrastructure/file_io.py](../../backend/infrastructure/file_io.py:9) 已集中 CSV、JSON、文本与 PDF 文件操作。
- [backend/core/factors.py](../../backend/core/factors.py:23) 已共用因子范围等数值处理。
- `backend/engines/` 中若干文件只是导入 `backend/core/` 实现的兼容入口，不是重复实现算法，不能按同名函数算作重复代码。

### 可进一步考虑，但优先级较低

- 参数面板中“标签＋控件＋间距”的行构建反复出现。可在已经完成控件工厂后评估小型布局辅助函数，不建议立刻把全部页面改为配置驱动的动态表单。
- 验证页与统计诊断页都绘制预测／观测、残差／预测图，可考虑共用单张图的绘制函数。两者分别组合两图和四图，且标注训练／留出数据来源，不能直接合并整页。
- 报告与界面都使用分析结果，但呈现目标和序列化约束不同。可继续共用结果数据，没必要让 PDF 报告继承 Qt 结果页面。

### 看起来相似但不应直接合并

- `result_summary.display` 会把非有限数值显示为破折号或正／负无穷；结果表格中的现有 5g／6g 规则不同。若统一格式，需先确认是否允许可见输出改变。
- `report_engine.serializable` 保留正负无穷的文本表示并过滤预测器；`workbench_analysis.clean_json` 将非有限浮点数置为空。两者业务策略不同，不能为了减少代码直接互换。
- `factors._isfinite` 返回布尔值；`design_analysis.finite` 返回数值或抛出异常。这不是同一接口的无意义重复。
- 报告仍使用 `anova_text/validation_text/model_text` 等内容，不能因为界面已有结构化结果就删除这些输出；实际消费者位于 `report_engine.py`。

## 建议顺序与减行判断

1. **优先：数值输入创建函数＋下拉框刷新函数。** 范围明确、已有局部工厂可演进，重点减少散落的重复设置，保留各参数的范围、默认值、精度和信号行为。
2. **其次：只读结果表填充与格式化适配。** 将三份相近单元格处理复用起来；摘要表、长表各自保留布局策略。
3. **再评估：结果分节、清理、参数行和绘图辅助。** 只在公用实现与调用代码合计确实更少、更清楚时保留。

本轮已确认的主要抽取候选是数值配置、下拉框刷新、只读表格填充、结果分节、动态清理、参数行布局和单张诊断图绘制这 7 组。其中后三组收益较小或需要更多接口核对。

本次不把创建点数量当成重复行数，也不给出未经实现验证的“已节省／保证可减少”行数。现有代码已有多处实质复用，预计低风险的第一批优化收益以数十行量级评估更合理；要给出净减行数，需完成选定重构后统计新增公共代码、修改调用和删除代码的总差额。不得用分号压行、删除必要注释或隐藏业务规则来制造减行效果。

## 核查结果

用户指出的方向成立，但三个方面成熟度不同：整数输入主要停留在 Qt 和样式复用；小数输入已有局部工厂；下拉框行为重复主要集中在刷新；结果视图已有真实的参数化框架，仍可继续统一基础表格与分节能力。建议从小型公共函数开始，不进行整个界面体系的重写。
